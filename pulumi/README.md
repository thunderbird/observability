# Pulumi Observability Infrastructure

We use Site24x7 to run checks against our services and alert us when problems arise. Much of that
configuration is defined here.


## Limitations

### Provider limitations

The Pulumi provider for Site24x7 is automatically generated by a `pulumi package` command. This
process seems to work pretty well in general, but it seems there are significant bugs either in the
original Terraform provider or being introduced by the repackaging process. There are many
inconsistencies between what the Terraform provider docs say about how this works and the practical
reality of working with the Pulumi-converted form of this provider.

The Terraform provider itself does not appear to have support for many resources supported by the
API and web console. This includes on call schedules. It does not appear to be possible currently
(someone please prove me wrong) to manage on call schedules with Pulumi or with Terraform, nor can
the monitors you create with Pulumi or Terraform be told to alert to an on call schedule.


### API limitations

The Site24x7 API depends in a lot of cases on special enumerations where meaningful effects are
indicated by numerical identifiers. Many of these are constants
[defined here](https://www.site24x7.com/help/api/#constants). The ones that we care most about have
been handled in code here such that we can use friendly names instead of hard-to-interpret numbers.
Check [site24x7_lib.py](site24x7_lib.py) for reference.

Some others are subject to change over time, such as their location data, and are only accessible
through authenticated API calls. A helper option, `refresh_site24x7_location_data`, has been added.
When true, this will cause the location data to be fetched and placed in a file on disk,
`site24x7-location-data.json`. This can be used as a reference when defining location profiles.

Some resources depend upon others, but we must specify those dependencies in the YAML config. This
would normally mean creating one resource (like a monitor group), waiting until it gets created,
then nabbing its ID and updating the YAML for a dependent resource (like a monitor) with it, then
running that change out. To help alleviate some of this, there are various options where the key
defining the dependency can be referenced by name where you need it.

- A `user_groups` entry's `users` list should list entries in the `users` mapping.
- A monitor group's `user_groups` list should list entries in the root `user_groups` mapping.
- A monitor's `location_profile`, `monitor_groups`, `user_groups`, and `notification_profile`
  options follow the same pattern.


### Work-in-progress considerations

Because this is a work in progress, resources managed by Pulumi have had a `(P)` added to their
display names. This serves as a visual indicator when using the web console.


## Alerting Organization

When a monitor is created in Site24x7, it can belong to a monitor group. This is an organizational
unit and not much more. Separately, it has a user group to which it alerts and a notification
profile that describes how to alert (email, text, phone call, mobile push notification). To capture
our differing alerting needs, we have the following organization structure:

- Each user has an account.
- User groups (alerting groups) refer to users who are members. We currently have one group for
  stage alerts and one for prod alerts. The member list of the prod alerts group are the people who
  are on call and responsible for the production environment.
- Notification profiles define how we notify. We have a low priority one that only ever notifies by
  email and a high priority one that notifies by all means necessary.
